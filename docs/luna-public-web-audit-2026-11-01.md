## 确认的设计机制

### 1. 自动刷新走无限预算旁路，重复采集并绕过 artifact 输出协议

`src/chrome/refresh-observer.ts:13` 明确传入 `budget: Number.MAX_SAFE_INTEGER`，随后第 19 行直接 `JSON.stringify(observation)` 构造成 user 消息。`src/agent/transport.ts:214` 起 drain 后把这些消息加入 initial，开启下一段执行。

日志证实同一次导航同时产生两种观察：事件 425 的动作后快照受 12,000 预算限制，事件 432 的自动刷新却带整页全部 11,521 项。后续 901/906、1203/1208 同样如此。这是同一页面通过两个输出通路重复提供；user 文本旁路没有普通 tool result 的 artifact 限额。

建议统一“页面稳定后采集”与“模型可读表示”：保留完整页面观察作为可复用 artifact，给模型有预算的入口、定向检索和明确分页。动作后已有相同文档/状态的新鲜观察时，刷新观察应复用它，不能再无限重取并全文注入。完整采集与一次性全部塞进上下文是两个独立要求。

### 2. 恢复执行时，压缩增量基线包含新巨型尾部，导致容量检查被抑制

`src/agent/compaction.ts:424` 的 `prepare()` 找到已有 checkpoint 后，先用完整 effective messages（包含 checkpoint 后新增的刷新消息）计算 baseEstimate，再在第 440 行把它作为 compactedBaseEstimate。`canCompact()` 第 393 行要求当前估值相对此值至少增长 10% 窗口。

当新段一开始就已有巨型刷新消息时，当前值与此“刚重设”的基线相同，增量为零。`src/agent/runner.ts:173` 把 `canCompact()` 与超过 80% 的容量条件相与；因此即使总量已远超过窗口，pressure 仍可为 false，继续发送请求。事件 912、1205、1214 与此机制一致：已有 checkpoint 626，巨型新尾部，估值超窗，实际仍发送，且没有新的 context.compaction.started。

建议以“上次真正完成压缩后的内容”设增量基线，不能把 checkpoint 之后的新尾部重设成已压缩基线；另在发送前对最终 outgoing 总量做硬性可容纳检查。不能用“避免重复压缩”规则绕过窗口正确性。

### 3. 大正文读取的交接成本使模型切换阅读路径

模型试图从 AX 分页切到正文：事件 73 的 read_text 成功，但事件 108 给的是 artifact 103 的明确访问路径，模型没有读取它便导航离开。早期三个 inspect 的大结果也都变成 artifact，唯一 read_artifact 只读五项。此后摘要明确缺 JWST 事实，解释了回访的必要性。

这里不能声称工具丢失了正文：artifact 确实保存且给出访问字段。能确认的是“先 inspect 大页 → 输出 artifact → 再读少量项 → 换读取方式 → 又得到 artifact”的多阶段交接，没有把用户需要的少数字段变成直接、可定位、可复用的证据。应优先改善可检索的正文/语义观察，以及结果如何提供字段入口；不要单纯扩大每轮快照预算。

## 修复后应验证的最终行为

1. 导航后既保留稳定完整观察，又只发送受预算的模型表示；同一次页面刷新不再重复无界注入。
2. 首次压缩后立即追加超过窗口的新刷新，发送前仍会压缩或转为可分页证据，不能直接发送超窗 prompt。
3. 原始任务、字段事实、来源 URL 和已读证据可跨压缩复用；模型无需重新导航只为取回已存的正文。
4. 用同一模型重跑本任务；分别记录事实正确性、实际页面访问、工具生命周期、请求体积和压缩区间，不能只检查 conversation.finished。

### 本次可确认的绕路

1. **同一轮在同一 tab 连续导航两个目的地。** 事件 37、38 同时发起 releases 和 Issues 导航。工具调度最终使它们按顺序完成，但模型没有先消费 releases 的必要字段再进入 Issues。第一次 Issues 动作后快照还报告 stale-observation；随后全页刷新与压缩接管了阅读。这不是两个彼此独立的读取任务，规划层应将“读取本页字段”与“离开本页”建立依赖。
2. **等价无效查询重复三次。** 事件 38、4715、6474 的查询解码后相同，第二次仅把空格编码从 `+` 换成 `%20`，第三次又回到 `+`；它们不是实质不同的查询恢复。两次额外导航没有检查标签定义、去掉一个过滤器作诊断、通过 UI 重新选择标签或采用其他新证据。事件 3163 已续读到 Invalid value；此后仅改 URL 编码不能解决 label 的语义有效性。
3. **误读自身侧栏。** 事件 6454 inspect 的 tab 是 990933948，事件 6457 返回 `chrome-extension://…/sidepanel.html`、标题 Surf Wax；任务站点 tab 则为 990933949。这一步对发布或 issue 核验没有业务价值。已有浏览器状态包含各 tab 身份，不能据此称工具隐去了 tab；可确认的是任务目标身份没有在选择时得到约束。
4. **收尾验收仍只接受“有成功观察”，没有核对未满足要求。** 事件 8226 以 completed 提交明确缺日期、缺 issue、缺时间的总结，事件 8227 接受并终结会话。它没有虚构三条 issue，但完成协议也没有要求对剩余要求继续恢复或说明已证实的外部依赖。改进应围绕逐项要求与证据的对应，不能靠工具调用成功推导任务完成。

这里没有工具失败循环或无限 get_job 轮询。对已有 cursor 续页（3163）以及读取 artifact（935）本身是合理的协议使用，应与无新增证据的等价重导航分开。
